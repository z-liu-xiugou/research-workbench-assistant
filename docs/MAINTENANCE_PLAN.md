建立日期：2026-09-27。状态：进行中；M01 已完成，其他项以任务表为准。

本文件是后续逐次维护的任务入口。用户每次可以指定一个编号，也可以说“继续维护仓库”，按下面的选择规则推进一个可验收的小任务。任务实际结果写入本表和工作日志，不依赖旧聊天记忆。

- 已有本地记录、修订历史、任务、备份恢复、显式关联、分页搜索、Crossref 检索和候选筛选。

## 2. 每次怎么推进

1. **确定范围**：优先处理用户指定编号；没有指定时，先看新出现的失败或明确缺陷，再从本表选择优先级最高、依赖已满足的一项。
2. **检查现场**：读取 `project-workbench/ACTIVE_CONTEXT.md` 和本文件；核对本地未提交改动、相关远端变更。只读与所选任务有关的文件。
3. **说明本轮目标**：用一两句话说明要解决什么、做到什么程度算完成。常规实现细节自行判断；涉及尚未确定的产品取舍时先给出具体选项。
4. **实施与验证**：完成一个任务或其中明确命名的子项。修复要有复现依据；文件写入、恢复和兼容性变化要验证失败场景。文档小改不机械新增测试。
5. **收尾记录**：在任务表更新状态、提交/PR/CI/文件证据；向 WORKLOG 追加结果；同步 CURRENT_STATUS 和 ACTIVE_CONTEXT 的下一步。
6. **报告边界**：分别说明本地实现、远端推送、CI、Release/Issue 状态。未运行或失败的检查明确写出，不提前标记完成。

默认每轮一项，不自动做完整张清单；遇到依赖缺失则记录阻塞原因，选择另一项可执行工作。严重的新缺陷可以插队，并在记录中说明原因。没有新变化时不为凑数量增加任务。

本次授权范围是建立维护计划；下列发布、升级和功能开发按用户后续逐次指令执行。正式发布使用届时核对过的版本与提交，不把本清单当作已发布证据。

## 4. 每项任务的范围和验收

### M01｜梳理版本与发布差异

**问题**：代码、首页和 Release 的版本信息落后程度不同，新用户可能拿到旧功能。

- [x] 比较最新 Release、标签、主分支和 CHANGELOG，列出尚未发布的功能与修复。
- [x] 核对脚本版本、技能说明、中英文 README 和升级指南，修正相互矛盾的表述。
- [x] 确定下一预览版编号和对应范围，保留 alpha/预览版定位。
- [x] 写好发布说明：新增功能、兼容性变化、升级方法、已知限制。

**验收**：所有版本入口一致；发布说明能对应代码和测试；未实现能力没有混入。此项完成仅代表发布准备就绪。

**主要位置**：`CHANGELOG.md`、`README.md`、`README_EN.md`、`docs/GETTING_STARTED.md`、技能和脚本的版本入口。

### M02｜验证用户实际拿到的分发包

**问题**：源码目录中测试通过，不等于下载包内容齐全且可以安装。

- [ ] 从选定提交生成与发布方式相符的分发包，检查包含文件，不携带私有参考材料、缓存或真实记录。
- [ ] 在隔离的临时目录解包安装，避免修改维护者正在使用的技能。
- [ ] 用虚构数据走通初始化 → 记录 → 搜索 → 查看 → 续接读取 → 备份 → 恢复。
- [ ] 覆盖带空格、中文的目录路径；检查说明书命令能按原样使用。

**验收**：记录所测提交、打包方式、环境和结果；恢复前后关键记录一致；已有安装不被覆盖。脚本续接检查不能替代 #9 的真人 Codex 对话验收。

### M03｜发布新预览版

- [ ] 核对 M01/M02 证据与待发布提交一致，检查该提交远端 CI。
- [ ] 核对标签和 Release 是否已存在，避免覆盖已有版本。
- [ ] 发布明确标为预览版的 Release，并附变更、升级方法和限制。
- [ ] 发布后核对标签指向、下载入口和版本显示，必要时复核实际下载包。

**验收**：提供 Release 链接、提交、标签和验证记录；文档中指向的版本确实可获取。只建立草稿时状态仍为进行中。

### M04｜一键只读诊断

**问题**：当前 `audit` 侧重工作台数据检查；用户还会遇到版本、目录、权限和锁文件问题。

- [ ] 明确诊断命令的输入和输出，区分安装环境检查与工作台检查。
- [ ] 检查 Python/工具版本、技能位置、必要文件、目录权限和锁文件存在情况。
- [ ] 对每类问题给出中文说明、建议操作和便于反馈的状态码。
- [ ] 提供脱敏输出方式，不让用户直接公开个人路径和研究内容。
- [ ] 测试正常安装、缺失文件、不可写目录、残留锁、损坏配置等情况。

**验收**：诊断不改写工作台、不自动删除锁；不能仅凭锁文件存在就断言其已失效。不证明 Codex 一定成功加载技能，也不把外部服务可访问等同于工作台健康。

### M05｜升级前先检查和备份

- [ ] 明确升级来源、当前版本、目标版本和安装目录，优先支持本地已取得的目标版本。
- [ ] 设计安装文件清单或其他可靠方法，识别用户修改过的技能文件；旧安装缺少基线时明确标为无法自动判定。
- [ ] 提供升级预览，列出将改变的文件及备份位置。
- [ ] 创建完整旧安装备份并验证可读取，排除用户项目目录。
- [ ] 检查安装中的并发冲突及目标路径边界。

**验收**：预览不改安装；无法完成备份时停止；不静默覆盖用户修改。新增清单必须兼容没有清单的旧安装。

### M06｜升级执行与回退

- [ ] 在临时目录准备新版本，检查完整性后再替换安装。
- [ ] 为复制失败、权限不足、替换失败和中断设计可恢复流程。
- [ ] 支持按已保存备份主动回退；校验备份来源和完整性。
- [ ] 增加 Windows/Linux 故障测试，覆盖冲突和重复执行。
- [ ] 更新面向初学者的升级/回退说明。

**验收**：成功时新版本可运行；失败时旧版可用或有明确可验证的恢复路径；不改用户科研项目。回退技能版本不等于回退用户数据，必须说明旧版对新数据的兼容边界。

### M07｜多关键词与命中片段

- [ ] 保留现有单字符串搜索默认语义，为多关键词增加明确选项，区分“全部包含”和“任一包含”。
- [ ] 在摘要中展示实际命中附近的文字，并控制长度。
- [ ] 保留分页上限、稳定排序、类型/状态筛选以及按 ID 查看完整记录。
- [ ] 测试中文、大小写、标点、空查询、多条件和跨页排序。

**验收**：旧调用仍可用；新规则在帮助中有例子；命中片段来自原文，不由 AI 编造；不宣称实现语义搜索。

### M08｜日期与历史版本

- [ ] 日期筛选先明确针对记录时间，和论文发表年份区分；定义时区与起止边界。
- [ ] 增加显式历史搜索选项，默认仍仅搜索当前有效记录。
- [ ] 历史结果显示是否已被替代及其当前版本入口。
- [ ] 测试修订链、多次替代、时间边界、组合筛选和分页。

**验收**：历史不会混充当前结论；不修改原始记录；无效时间范围有清晰错误提示。

### M09｜明确文献导入协议

**建议起点**：先评估 RIS 作为首个格式；尚未确认支持格式，实施时根据虚构样例和解析成本确定，不同时承诺 RIS/BibTeX/CSV 全覆盖。

- [ ] 准备虚构样例，覆盖多作者、中文、缺 DOI、缺年份、多行内容和异常输入。
- [ ] 定义题名、作者、年份、来源、DOI、摘要和原始标识如何映射。
- [ ] 明确导入为候选元数据，不自动生成精读笔记或已读状态。
- [ ] 记录编码、大小限制、字段缺失及不支持字段的处理规则。

**验收**：形成可执行的字段表、样例和错误处理规则；说明首版支持范围。只做本地文件导入，不等同于 Zotero 双向同步。

### M10｜文献导入预览与写入

- [ ] 先显示新增、重复、跳过和错误数量，逐条提供原因。
- [ ] DOI 归一化与现有候选/笔记去重逻辑保持一致。
- [ ] 按 M09 定义的规则显式执行导入，保存批次、来源和时间。
- [ ] 明确批次失败时是整体拒绝还是允许可追溯的部分导入，并验证中断不会产生无法解释的半成品。
- [ ] 重复导入同一文件不重复创建相同 DOI 候选。

**验收**：预览不写入；失败和跳过条目可检查；已有笔记和阅读状态不被覆盖；新增记录可备份恢复。

### M11｜无 DOI 疑似重复

- [ ] 建立题名规范化规则，结合作者与年份提示疑似重复。
- [ ] 显示判定依据和两条记录，保留人工选择。
- [ ] 先支持“标记待核对/保留不同条目”，不自动删除或合并。
- [ ] 用同名不同论文、中英文题名、预印本和正式版等样例检查误判。

**验收**：疑似重复只是提示；不得因此丢失原条目；记录判断理由，可撤回错误判断。若后续需要合并功能，另列任务设计引用迁移。

### M12｜依赖更新提醒

- [ ] 核实现有配置及可用的 GitHub Actions 依赖更新方式，限定更新频率和并行数量。
- [ ] 自动提出更新 PR，并保持完整提交 SHA 固定。
- [ ] 更新 PR 运行当前测试矩阵和公开文件检查。
- [ ] 说明人工审查和失败处理方式；不自动合并。

**验收**：配置有效、范围仅限声明的依赖；实际产生更新时核对行为。没有新版本时，不把“未出现 PR”当作故障，也不声称已观察到自动更新成功。

### M13｜持续验证分发包

- [ ] 把 M02 的可重复步骤接入 CI，按成本决定每次提交或发布候选时触发。
- [ ] 在隔离目录安装打包产物，而非直接引用源码树运行。
- [ ] 验证包中必要文件和安装后基础流程，保留失败日志。
- [ ] 避免重复完整测试造成无意义耗时；明确与已有源码测试的分工。

**验收**：能够通过故意缺少必要文件的测试样例发现打包遗漏；正常包在声明支持的环境通过；不污染已有安装。

### M14｜数据增长与维护性评估

- [ ] 用虚构数据建立约 100、1000、10000 条记录的测量样例，说明正文长度和修订比例。
- [ ] 测量搜索、审计、重建和备份的耗时/输出规模，记录环境。
- [ ] 找出实际瓶颈，再决定是否需要缓存、索引或模块拆分。
- [ ] 如引入索引，明确原始记录仍为事实来源，索引可丢弃重建。

**验收**：交付测量结果和是否优化的判断；不凭直觉改架构。具体性能目标基于测量再定，若需大改另拆实现项。

### M15｜外部反馈与 #9

- [ ] 用户安排志愿者按 `docs/USER_TRIAL.md` 试用，使用虚构数据。
- [ ] 保存脱敏环境、版本、完成步骤、失败信息和反馈来源。
- [ ] 对实际缺陷复现、查重，必要时建立独立修复任务。
- [ ] 验证安装、技能发现、新对话续接及备份恢复是否满足原 Issue 验收。

**验收**：以真实反馈判断 #9 是否完成；脚本测试和 AI 自测不能代替。暂时无人试用就维持待确认，不反复催促，不影响独立维护。
